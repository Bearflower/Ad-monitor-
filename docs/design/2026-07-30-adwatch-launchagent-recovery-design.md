# Adwatch macOS 定时任务持久化与故障闭环设计

日期：2026-07-30
状态：设计已确认，实施与重启验收尚未开始

## 一、背景

Adwatch 原生产 LaunchAgent 指向
`/Users/yl/Documents/跨境电商/广告盯盘自动化`。2026-07-29 09:00
任务曾正常执行并发送 2026-07-28 日报；Mac 于 10:19 重启后，
`com.adwatch.daily` 未在新登录会话中恢复。2026-07-30 09:07 检查时，
`launchctl` 返回服务不存在，且当时没有生成 2026-07-29 日报。

现有 plist 文件虽然存在、格式正确，但安装流程只完成了当次登录域注册，
没有把代码目录、配置、启用状态、登录加载和运行后验收作为一个可重复执行的
整体。同时，已安装任务使用旧代码目录，当前维护仓库则是
`/Users/yl/vscode/Cross_Border_Electronic_Commerce`，形成代码、数据和运行
配置漂移。

当前代码还存在以下缺口：

- plist 渲染时间与 `.env` 中的计划时间没有统一。
- `run daily` 没有在广告采集前独立完成紫鸟 Bridge 门禁。
- 采集故障只进入普通标准错误日志，没有独立故障日志和专用飞书通知。
- 登录后没有“已过 09:00 且当天漏跑”的补偿判断。
- 汇率同步使用日报数据日期，无法表达“执行日汇率优先”的新口径。
- ECB 最近有效值可能被标记为请求日新值，真实来源日期未被持久化。

## 二、建设目标

1. 以 `/Users/yl/vscode/Cross_Border_Electronic_Commerce` 作为唯一生产
   代码源，以该目录下 `.env` 和 `var/` 作为唯一生产配置与数据源。
2. 注销所有指向旧目录的 Adwatch 定时任务，从唯一代码源注册
   `com.adwatch.daily`。
3. 按 `Asia/Shanghai` 每天 09:00 执行，登录后能够识别并补偿当日漏跑。
4. 每次广告采集前检查紫鸟 Bridge；不可用时阻止采集并形成独立故障闭环。
5. 采集失败时保留结构化故障日志，并补发去重的飞书故障卡片。
6. 每日先解析执行日汇率，再采集广告和订单数据，最后进行利润分析和报告。
7. 通过自动化测试、当前会话安装验证、重新登录或重启验证以及次日
   09:00 实际运行验证，证明定时任务持久化有效。

## 三、非目标

- 不引入系统级 LaunchDaemon、独立 macOS 应用或管理员常驻服务。
- 不恢复旧目录作为生产运行路径。
- 不改变广告策略、审批、Shadow 或 Live 写入边界。
- 不在本次修复中更换飞书机器人或汇率数据供应商。
- 不以模拟数据代替真实运行验收。

## 四、方案选择

### 4.1 采用方案

采用“单一受管 LaunchAgent + 到期判断包装器”：

- LaunchAgent 同时配置 09:00 日历触发和 `RunAtLoad=true`。
- 09:00 触发执行正常日报；登录触发只做是否漏跑判断。
- 安装、状态查询、卸载和修复由 Adwatch CLI 统一管理。
- 运行状态、故障证据和飞书通知状态由独立运维组件记录。

该方案符合 macOS per-user LaunchAgent 的原生登录加载机制，能够在不引入
管理员服务的情况下处理登录后漏跑，并且容易进行自动化测试和现场验证。

### 4.2 未采用方案

- 双 LaunchAgent：日报任务与守护任务仍依赖同一个用户登录域扫描，不能形成
  真正独立的恢复通道，且增加重复触发与维护成本。
- 系统 LaunchDaemon 或登录应用：需要管理员权限或应用打包，并且系统上下文
  不适合访问紫鸟 GUI Bridge，超出当前项目边界。

## 五、组件边界

### 5.1 定时任务管理

新增独立运维模块，负责：

- 根据配置生成 plist。
- 安装前验证项目目录、`.venv/bin/adwatch`、`.env`、日志目录和系统时区。
- 提供 `adwatch schedule install|status|uninstall|repair`。
- 比较期望配置、已安装 plist 和 `launchctl` 运行状态。
- 以原子方式替换 plist，并在替换前保存可恢复备份。
- 验证服务标签、执行路径、工作目录、09:00 触发器和 `RunAtLoad`。

CLI 只负责解析参数和呈现结果，不直接承载 plist、`launchctl` 或状态判断逻辑。

### 5.2 计划运行包装器

新增 `adwatch run scheduled-daily`，负责：

- 统一使用 `Asia/Shanghai` 计算执行日期和日报数据日期。
- 通过进程锁防止并发执行。
- 判断当前触发是 09:00 正常运行、登录后补跑还是无需执行。
- 编排汇率、Bridge、广告采集、订单同步、分析、报告和通知。
- 记录每个阶段的开始、完成、失败和退出码。

现有 `adwatch run daily` 保留为显式日期运行入口，并增加 `--no-notify`，
供人工补跑和故障排查使用。

### 5.3 故障记录与通知

新增独立运维事件组件，负责：

- 将故障追加到 `var/logs/adwatch-faults.jsonl`。
- 在 `var/operations/daily-schedule-state.json` 中记录最近一次运行和通知
  去重键。
- 生成不包含密钥、Webhook 或完整敏感响应的错误摘要。
- 使用现有 `FEISHU_WEBHOOK` 发送红色故障卡片。
- 保证飞书发送失败不会覆盖原始运行故障。

### 5.4 汇率解析

扩展汇率集成模块，区分：

- `rate_date`：汇率应用到的广告数据日期。
- `source_date`：汇率实际公布或本地来源日期。
- `resolution_status`：执行日值、昨日回退或最近交易日回退。
- `resolved_at`：北京时间解析时间。

通过数据库迁移为现有 `exchange_rates` 增加可空的 `execution_date`、
`source_date`、`resolution_status` 和 `resolved_at` 字段。旧记录继续兼容，
新计划任务必须完整写入来源信息。远程汇率适配器必须保留 ECB 的实际公布
日期，不能把前一交易日的值伪装成请求日新值。

## 六、配置

禁止把业务时间、重试次数和回退窗口直接写死在业务逻辑中。默认值由配置层
集中提供，并允许 `.env` 覆盖：

- `ADWATCH_DAILY_RUN_TIME=09:00`
- `ADWATCH_TIMEZONE=Asia/Shanghai`
- `ADWATCH_BRIDGE_RETRIES=3`
- `ADWATCH_BRIDGE_RETRY_DELAY_SECONDS=10`
- `ADWATCH_EXCHANGE_RATE_MAX_STALENESS_DAYS=7`

安装和状态查询必须显示最终生效值。系统时区不是 `Asia/Shanghai` 时，
`schedule install` 拒绝安装，`schedule status` 返回不健康状态。

## 七、安装、修复与卸载

### 7.1 安装

`schedule install` 按以下顺序执行：

1. 解析唯一项目目录并验证运行依赖。
2. 创建 `var/logs/` 和运维状态目录。
3. 渲染期望 plist，并先写入项目 `var/` 作为可审计安装源。
4. 备份当前 `~/Library/LaunchAgents/com.adwatch.daily.plist`。
5. 扫描用户 LaunchAgents 中由 Adwatch 生成且仍引用旧目录的 plist，记录
   精确标签和路径；不得处理非 Adwatch 任务。
6. 对确认的旧服务逐个执行 `bootout`；服务不存在视为幂等状态。
7. 删除或替换所有指向旧目录的 Adwatch plist。
8. 明确启用服务，向当前 `gui/<uid>` 域执行 `bootstrap`。
9. 查询 `launchctl` 并验证路径、工作目录、触发时间和 `RunAtLoad`。

任一步失败即停止后续操作，并保留备份、命令结果和故障日志。

### 7.2 状态与修复

`schedule status` 同时检查：

- plist 文件存在且格式有效。
- plist 与当前代码生成结果一致。
- 服务在当前 GUI 登录域中可查询。
- 服务未被 disabled。
- 执行路径和工作目录只指向唯一代码源。
- 09:00 和 `RunAtLoad` 均已注册。
- 最近运行状态、故障状态和下一次应执行日期可解释。

`schedule repair` 只在发现漂移时重新生成并注册；健康状态下不得重复重载。

### 7.3 卸载

`schedule uninstall` 只操作精确标签 `com.adwatch.daily` 和已解析的精确 plist
路径，不使用目录级删除或模糊匹配。卸载前保存备份，完成后确认
`launchctl` 中不存在服务。

## 八、运行与幂等

### 8.1 日期规则

包装器以北京时间计算：

- `execution_date`：任务实际执行日期。
- `report_date`：`execution_date - 1 天`。

09:00 日历触发始终尝试执行 `report_date`。登录触发时：

- 北京时间未到 09:00：记录无需执行并退出。
- 已到 09:00 且 `report_date` 已成功：幂等退出。
- 已到 09:00 且 `report_date` 未成功：执行一次补跑。

### 8.2 运行锁与状态

每次运行先获取 `var/operations/scheduled-daily.lock` 非阻塞锁。锁已被占用时
记录重复触发并退出，不启动第二条流水线。
独立状态至少记录：

- 运行 ID、触发来源、执行日期和日报日期。
- 开始与结束时间。
- 当前阶段和最终状态。
- 退出码、错误类型和错误摘要。
- 飞书通知状态与去重键。

只有汇率解析、所需采集、分析和本地报告均达到定义的成功条件时，才能记录
当天成功。部分成功不得伪装成完整成功。

## 九、汇率规则与执行顺序

### 9.1 汇率选择

以 2026-07-30 09:00 执行并分析 2026-07-29 为例：

1. 优先寻找 2026-07-30 的 THB/CNY 汇率。
2. 当天没有公布值时，使用 2026-07-29 的汇率。
3. 昨天也没有值时，使用执行日前 7 天内最近有效交易日汇率。
4. 将选定值写入 2026-07-29 的分析汇率记录。
5. 同时保存实际 `source_date`、解析状态和解析时间。

网络请求失败时使用同样优先级查询本地汇率。超过配置窗口或完全无值时，不
生成无依据汇率。

### 9.2 完整顺序

```text
获取运行锁与判断是否到期
→ 解析执行日汇率并应用到日报数据日期
→ 检查紫鸟 Bridge
→ 采集广告数据
→ 同步订单数据
→ 执行利润与策略分析
→ 生成质量报告和经营日报
→ 发送普通日报
→ 写入最终运行状态
```

汇率完全不可用时，广告和订单采集仍继续，利润分析保留待补状态，并记录和
发送汇率故障。紫鸟 Bridge 在配置次数内仍不可用时，不进入广告采集，记录
独立故障并发送飞书故障卡片。

单个平台采集失败时保留其他平台数据和部分日报，同时额外发送故障卡片。

## 十、故障日志与飞书通知

故障日志采用一行一个 JSON 对象，至少包含：

- 事件时间、运行 ID、执行日期和日报日期。
- 失败阶段、错误类型、脱敏摘要和退出码。
- 是否可重试、重试次数和本地报告路径。
- 飞书通知状态。

同一日报日期、同一失败阶段和同一错误类型形成稳定去重键。去重键已经发送
成功时，登录补跑不得重复刷屏；故障内容变化或日期变化时允许发送新通知。

飞书故障卡片使用红色标题，展示失败阶段、数据日期、简短原因、已完成步骤、
本地日志路径和建议检查项。卡片不包含 `.env` 内容、Webhook、店铺凭据或
完整外部响应。

`--no-notify` 禁止普通日报和故障卡片的所有外部发送，但不得禁止数据库写入、
质量报告、经营日报、运行状态或故障日志。

## 十一、旧任务迁移与 2026-07-29 补跑

实施顺序：

1. 完成代码和自动化测试。
2. 保存当前已安装 plist 与 `launchctl` 状态快照。
3. 注销指向旧目录的 `com.adwatch.daily`。
4. 从唯一代码源执行 `schedule install`。
5. 执行 `schedule status`，确认系统中没有旧目录引用。
6. 从唯一代码源补跑 2026-07-29，显式使用 `--no-notify`。
7. 验证当前 `var/` 中的数据库、质量报告、日报和运行日志。

旧目录中 2026-07-30 20:49 生成的 2026-07-29 日报只作为历史证据，不作为
新生产数据源，也不再次触发飞书发送。

## 十二、测试设计

### 12.1 单元测试

- plist 使用唯一项目路径、09:00、`RunAtLoad` 和配置化环境。
- 执行时间早于 09:00、漏跑、已成功和并发锁四种到期判断。
- Bridge 首次成功、重试后成功和达到上限失败。
- 故障 JSONL 字段完整、敏感信息脱敏和飞书去重。
- `--no-notify` 禁止所有外部通知，但保留本地产物。
- 汇率执行日命中、昨日回退、周末或节假日回退和超过 7 天拒绝。
- 选定汇率应用到 `report_date`，同时保存真实 `source_date`。

### 12.2 集成测试

- 汇率解析发生在 Bridge、广告采集和分析之前。
- Bridge 失败时不调用广告采集。
- 单平台采集失败时保留另一平台数据、生成部分日报并发送故障卡片。
- 飞书发送失败时保留原始运行故障。
- `schedule install`、重复安装、状态查询、修复和卸载使用可替换命令适配器
  验证完整调用顺序，不在测试中修改真实 LaunchAgent。

### 12.3 回归验证

- 全量 pytest 通过。
- Ruff 对 `src` 和 `tests` 无错误。
- 配置、CLI 帮助、README 和运维文档与实际命令一致。
- 检查新增代码不存在业务阈值、时间和延迟硬编码。

## 十三、现场验收

### 13.1 当前会话

- 旧服务已注销，旧 plist 已备份。
- 新服务路径和工作目录均为唯一代码源。
- `launchctl print` 显示 09:00 触发器和 `RunAtLoad`。
- 重复执行安装不产生第二个任务。
- 2026-07-29 在当前 `var/` 补跑成功，本次没有飞书外发。

### 13.2 重新登录或重启

重启会中断当前协作和本机进程，实施时必须在执行前再次取得用户明确确认。
重新登录或重启后检查：

- `launchctl print gui/<uid>/com.adwatch.daily` 可直接找到服务。
- plist、执行路径、工作目录和 09:00 触发器无漂移。
- `RunAtLoad` 在 09:00 前只记录无需执行；09:00 后漏跑时只补跑一次。
- Bridge 或采集故障能够留下独立日志和去重飞书卡片。

### 13.3 次日 09:00

次日 09:00 后必须检查：

- 当天服务在触发前后均存在。
- 运行状态记录了汇率、Bridge、采集、分析和报告各阶段。
- 数据库、质量报告和日报日期正确。
- 成功运行发送一份普通日报；失败运行发送一份去重故障通知。
- 日志中不存在旧目录路径。

在重启或登录验收和次日 09:00 实际运行均有证据前，不得把持久化验收标记为
完成。

## 十四、风险与回滚

### 14.1 主要风险

- macOS 时区变化导致日历触发与北京时间不一致。
- 登录时紫鸟尚未完全启动，Bridge 探测产生短暂失败。
- 汇率源在周末、节假日或网络故障时无新值。
- 安装过程中断导致 plist 已替换但服务尚未注册。
- 当前工作树有其他未提交改动，修复不得覆盖无关文件。

### 14.2 控制措施

- 安装和状态查询验证时区、路径与服务域。
- Bridge 使用配置化有限重试，不进行无限等待。
- 汇率使用有界回退并保存真实来源。
- plist 原子替换、安装前备份、每一步失败即停止。
- 只修改本需求涉及文件，Git 暂存使用精确路径。

### 14.3 回滚

若新任务安装或运行异常：

1. 注销当前新服务。
2. 恢复安装前保存的 plist 备份，但不得恢复任何指向旧代码目录的配置。
3. 在唯一代码源中人工执行带明确日期的 `run daily`。
4. 修复后重新运行测试、安装和状态验证。

回滚仅恢复调度能力，不恢复旧目录作为生产源。

## 十五、完成标准

以下条件全部满足后，本需求才可完成：

- 自动化测试、代码检测和代码审查通过。
- 唯一代码源能够管理 LaunchAgent 全生命周期。
- 系统中不存在旧目录定时任务或路径引用。
- 2026-07-29 已在当前生产数据目录完成禁通知补跑。
- Bridge、汇率、采集和飞书故障均有独立可审计记录。
- 重新登录或重启后服务自动存在。
- 次日 09:00 真实运行证据完整。
