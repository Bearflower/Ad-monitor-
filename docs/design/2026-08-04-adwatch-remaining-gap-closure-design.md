## 1. 目标

以根目录 `findings.md` 的 45 项端到端能力矩阵为唯一验收基线，在已完成
Shopee 商品/订单同步和 `/inventory` 成本闭环之后，按业务数据依赖关闭
剩余 25 项不完整能力。

本轮采用“业务数据真实性优先”：先补退款、物流、库存、结算和平台费等
上游事实，再重算利润和经营页面，之后完善财务、广告明细、审批、周期
报告、实验和生产验收。

## 2. 完成定义

一项能力只有同时满足以下条件才可从 `部分实现/未实现` 改为 `已实现`：

1. 有真实数据源或明确的人工输入边界；
2. 有幂等、可追溯的本地事实存储；
3. 有业务服务消费这些事实；
4. 有 CLI、页面或定时任务入口；
5. 有自动化测试和脱敏真实样本验收；
6. 失败会留下独立运行记录和故障状态；
7. README、运维文档和 `findings.md` 与代码事实一致。

只有数据类、协议、测试桩、占位页或计划文档，不算完整实现。

## 3. 范围与后置项

### 3.1 本计划实施范围

- Shopee 退款 T+3、物流和平台库存事实；
- Income PDF、结算、平台费和广告充值；
- 利润回算、来源新鲜度和经营页可信度；
- 费用、凭证、余额对账、库存调整、分润与冲销；
- Shopee Campaign/SKU 广告明细；
- 策略规则维护、审批和执行审计页面；
- 真实周报、月报和每周调度；
- 实验体系和备用采集；
- readiness、连续三日对账、服务器部署和生产验收。

### 3.2 显式后置

TikTok 真实采集保留为 45 项矩阵中的部分实现项，但当前由产品决策禁采。
只有用户重新启用 TikTok 后，才执行真实账号读取、Campaign 明细、selector
和现场对账。任何批次都不得为了“清零缺口”擅自重新启用 TikTok。

官方平台 API/OAuth 仍为可选增强，不进入主线完成门槛。

## 4. 总体架构

```text
紫鸟内已登录 Shopee 页面 / Income PDF / 人工受控输入
                         │
                         ▼
              只读适配器、解析、拒绝与隔离
                         │
                         ▼
      SQLite 平台事实 + 来源时间 + 观测时间 + 运行记录
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
         订单与库存    利润与策略    财务与分润
              └──────────┼──────────┘
                         ▼
               Read Model / 页面 / 报告
                         │
                         ▼
                飞书通知与审批回链
```

SQLite 在本地阶段继续作为唯一业务事实来源。服务器部署前单独设计持久卷、
备份、恢复和单实例运行方式；不在功能开发中顺便迁移到 PostgreSQL。

## 5. 数据原则

### 5.1 平台事实与业务解释分离

退款、物流、库存、结算、平台费和广告充值先保存为平台事实；利润、现金、
库存余额和策略建议只读取事实，不直接解析页面或 PDF。

### 5.2 缺失不是零

每个利润输入都保存来源、来源日期和 `fresh/stale/missing` 状态。无法从
Shopee 获得退款金额时保存状态事实并将金额标为缺失，不允许写成 `0`。

### 5.3 历史可修正但必须可追溯

- 退款按配置的 T+3 窗口每日回看；不同观测日保留历史快照；
- 物流与库存按观测日保存，不覆盖历史日期；
- 结算原始事实不可无痕修改，修订版保留文件哈希和审计；
- 人工财务、库存和分润通过确认、调整或冲销修正，不物理删除。

### 5.4 外部安全边界

- 紫鸟链路只允许固定 Shopee URL 的导航和只读请求；
- 不保存会话参数、买家姓名、电话、地址或银行账号；
- 外部能力各自记录运行状态，单项失败不得删除旧事实；
- `ADWATCH_LIVE_WRITES=false` 在整个计划中保持关闭。

## 6. 分批设计

### P1-A：退款、物流和平台库存

复用现有 `ShopeeOrderSync`、Item/Model/Seller SKU 映射和订单行。先冻结
脱敏真实响应字段，再增加退款观测、物流观测和库存历史快照；日任务按
配置回看 T+3，缺失字段显式降级。

### P1-B：Income、结算、平台费和广告充值

复用已确认的 Income 设计和现有 `CommerceRepository`。PDF 以 SHA-256
幂等，费率按覆盖周期选择，充值、消耗、结算和收入确认保持独立口径。

### P1-C：利润回算和经营可信度

为每个利润输入增加来源与新鲜度，提供日期范围重算命令。经营页可以从
利润数字穿透到订单、退款、成本、库存和结算来源；缺输入时展示降级原因。

### P1-D：财务、库存和分润闭环

完成费用确认/冲销、凭证哈希、银行余额、三方差额、收入调整、人工库存
调整和分润冲销。专属业务页面提供受控入口，所有写入保留 actor、原因和
审计事件。

### P2-A：Campaign/SKU 广告明细

保留现有总览作为对账层，增加分页 Campaign/SKU 明细。明细合计必须在
配置容差内匹配平台总览，超差进入隔离，不覆盖已验收事实。

### P2-B：策略和审批审计页面

增加策略版本新增/生效/关闭入口，实现 `/approvals` 列表、详情、过期、
执行前后证据、回读、回滚和熔断时间线，只在 Shadow 模式验收。

### P2-C：周报、月报和每周调度

周/月报告使用周期聚合，不拼接日报。周任务有独立锁、状态、登录补跑、
通知去重和故障记录，与每日任务互不抢占。

### P2-D：实验和备用采集

实验对象、窗口、护栏和结果状态机独立于普通策略；备用采集只有主链连续
失败达到配置门槛后启用，并保存来源和切换证据。

### P3：生产验收和服务器部署

补齐 readiness，迁移 selector 证据，完成 Shadow/回滚/故障演练与连续
三日不低于 99% 对账。部署是独立批次，不与功能开发混合。

## 7. 服务器发布设计

### 7.1 两个发布检查点

1. P1-C 完成后可发布“只读经营版”：真实上游、利润和经营页可解释，
   `ADWATCH_LIVE_WRITES=false`；
2. P3 全部验收后发布“正式生产版”：仍默认关闭广告 Live，只有另行批准
   精确白名单才允许开启。

### 7.2 部署规则

部署时使用 `.trae/rules` 和【服务器自动化部署】技能，但所有 IP、SSH
密钥、目录、容器名、端口和健康检查必须来自本项目专属配置，不照搬技能
中的示例。

部署必须包含：

- SSH 密钥认证和最小权限检查；
- 服务器单一项目目录、单一应用容器；
- SQLite、配置和报告目录的部署前可恢复备份；
- 部署包文件清单与 SHA-256 完整性校验；
- 镜像/容器版本标识和关键代码文件哈希对比；
- 持久卷、容器健康、应用只读接口、定时任务和故障日志验证；
- 回滚到上一版本并恢复数据库副本的演练记录。

任何清理旧目录、旧容器或旧镜像的操作，都必须先解析确切目标并获得用户
对破坏性动作的明确授权。

## 8. 测试与质量门禁

每个批次遵循：

```text
失败测试（RED）
→ 最小实现（GREEN）
→ 相关模块回归
→ 全量 pytest / Ruff / compileall / git diff --check
→ 脱敏真实只读样本
→ 代码审查与文档对照
→ findings 能力矩阵更新
```

涉及数据库的批次必须测试迁移幂等、唯一键、旧库升级和备份恢复。涉及页面
写入的批次必须测试 CSRF、校验、审计、重复提交和冲销。涉及定时任务的
批次必须测试锁、失败隔离、补跑、通知去重和重启恢复。

## 9. 任务管理与中断规则

根目录 `task_plan.md` 是任务状态来源，`progress.md` 记录每批实际证据和
错误。每完成一个阶段立即更新状态，不把计划文件存在视为代码完成。

正常技术取舍不中断用户。只有以下情况暂停并请求确认：

- 需要新的服务器地址、密钥或外部账号权限；
- 需要启用真实广告写入或 TikTok；
- 需要删除、覆盖或不可逆迁移生产数据；
- 真实平台字段与已确认业务口径冲突；
- 同一阻塞条件经过不同方案仍无法解决。

## 10. 验收结论

项目完成时重新机械统计 45 项矩阵。除用户明确后置的 TikTok 外，所有项目
必须为“已实现”并有代码、入口、自动化和真实证据；TikTok 必须显示为
“按产品决策禁用”，不能被误报为完成。
