# AdWatch 一体化经营、进销存与投放系统设计

日期：2026-07-28  
运行环境：macOS 本机  
数据存储：SQLite  
真实广告写入：默认关闭

## 1. 目标

在现有 TikTok/Shopee 广告监控系统内增加经营记账、合伙人资金、
轻量进销存和利润分配能力。用户只使用一个本地 Web 入口完成查看、
填写、对账和审批；紫鸟 CLI、定时采集、分析、SQLite 和飞书通知在
Mac 后台协同运行。

系统必须做到：

- 每条订单 SKU 明细都能匹配确定的单位成本；
- 经营利润、现金余额和库存余额使用不同口径并能相互对账；
- 人工维护项可写、可追溯，已确认记录不能被无痕覆盖；
- 合伙人出资按洁云 50%、苏姐 50% 对账；
- 经营净利润按洁云 60%、苏姐 40% 分配；
- Excel 仅用于首次批量导入、备份和导出，不作为日常主数据库；
- 未完成现场验收前，真实广告写操作保持关闭。

## 2. 产品边界

### 2.1 自动获取

- Shopee/TikTok 订单、订单状态、退款、物流和平台结算数据；
- TikTok/Shopee 广告消耗、转化、GMV 和 Campaign 数据；
- 可由平台或紫鸟 CLI 获取的 SKU、商品和库存信息；
- 已配置数据源提供的汇率、平台费及其他经营指标。

### 2.2 人工可写

- SKU 单位成本及生效日期；
- 无法从平台获取的经营费用；
- 合伙人出资、代垫、提款和资金调整；
- 采购入库、额外物流、关税、包装等采购成本；
- 退货重新入库、报损和人工库存调整；
- 分润确认、实际支付和冲销；
- 需要人工解释的备注、凭证和对账调整。

### 2.3 不纳入本阶段

- Windows 迁移；
- 多企业、多租户和公网 SaaS；
- 复杂仓库波次、库位、序列号和生产制造；
- 未经审批的自动广告写入；
- 强制追踪每个订单到具体采购批次。

## 3. 总体架构

```text
紫鸟 CLI / 平台导出 / 外部数据源
                 |
                 v
        采集、清洗、去重、质量检查
                 |
                 v
           AdWatch SQLite
       /           |            \
广告监控       订单与库存       记账与分润
       \           |            /
                 v
          本地统一 Web 前端
                 |
                 v
         飞书提醒、审批与回链
```

SQLite 是唯一业务事实来源。Web、报表、飞书和分析结果均从 SQLite
读取；Excel 导入必须经过表头、类型、重复键和业务规则校验。

## 4. 核心数据模型

### 4.1 SKU 与成本

- `sku_master`：平台、店铺、Seller SKU、商品名称、规格、状态；
- `sku_aliases`：平台商品 ID、Model ID、历史 SKU 和 ERP SKU 映射；
- `sku_cost_history`：Seller SKU、生效日期、人民币单位成本、来源、
  备注、创建人和创建时间；
- `order_lines`：订单号、Seller SKU、数量、订单状态、退款数量；
- `order_cost_snapshots`：订单行实际采用的成本版本、单位成本和总成本。

成本按订单日期匹配当时有效的 `sku_cost_history`。订单成本确认后保存
快照，后续新增成本版本不会改变已经结账的历史订单。更正历史成本时
生成调整记录并重新执行受影响期间的对账，不直接覆盖原快照。

### 4.2 采购与库存

- `purchase_receipts`：采购单、供应商、日期、币种、付款状态；
- `purchase_lines`：SKU、数量、采购单价、采购金额和附加成本分摊；
- `inventory_movements`：入库、销售出库、退货入库、报损、人工调整；
- `inventory_balances`：按平台、店铺、SKU 汇总的可用库存和在途库存。

库存恒等式：

```text
期初库存 + 采购入库 + 销售退回 - 销售出库 - 报损 ± 人工调整 = 期末库存
```

采购付款影响现金，不直接扣减经营利润。商品随订单出库时，订单成本
快照才计入销售成本。取消订单不出库；退款退货根据实际物流结果决定
重新入库或计入报损。

本阶段不强制订单追踪到具体采购批次。采购入库计算出的综合单位成本
可以形成新的成本建议，经人工确认后写入 `sku_cost_history`。

### 4.3 费用和现金

- `expense_entries`：日期、类别、金额、币种、人民币金额、付款人、
  凭证、备注和状态；
- `capital_entries`：合伙人、应缴、实缴、代垫、返还和调整；
- `withdrawal_entries`：提款人、金额、日期、用途和状态；
- `cash_movements`：由销售回款、采购付款、费用、出资、提款和分润
  生成的统一现金流水。

所有人民币换算必须保存原币金额、币种、采用汇率和人民币金额，确保
以后可以按原始凭证复核。

### 4.4 分润

- `profit_periods`：结算期间、收入、销售成本、平台费、广告费、
  经营费用、净利润和结算状态；
- `profit_allocations`：洁云 60%、苏姐 40% 的应分金额；
- `profit_payments`：实际支付日期、金额、收款人和凭证。

出资比例与利润比例独立：

- 出资目标：洁云 50%、苏姐 50%；
- 净利润分配：洁云 60%、苏姐 40%。

分润先生成草稿，人工核对后确认。已确认记录不得直接修改；错误通过
冲销或调整单处理。

### 4.5 审计

所有人工写入必须记录：

- 创建时间、创建人和来源；
- 修改前后值；
- 关联业务对象；
- 修改原因；
- 草稿、已确认、已冲销等状态。

删除操作使用逻辑作废，不物理删除财务和库存流水。

## 5. Web 前端

### 5.1 今日经营

- 收入、订单、广告消耗、平台 ROAS、真实利润 ROAS；
- 净利润、现金余额、库存金额；
- 缺成本、缺映射、退款、库存和对账异常；
- 待审批广告动作与待确认分润。

### 5.2 SKU 与库存

- 待补 SKU 成本列表；
- 在线新增成本版本；
- SKU 映射与历史成本查询；
- 采购入库、库存流水和库存余额；
- 订单到成本快照的穿透查询。

### 5.3 记账对账

- 新增费用、出资、代垫、提款和调整；
- 上传或登记凭证；
- 50%/50% 出资差额；
- 现金账、平台结算和银行余额对账；
- 异常差额及修复入口。

### 5.4 分润审批

- 按期间生成可解释的净利润；
- 展示收入、销售成本、平台费、广告费和经营费用；
- 自动计算 60%/40% 应分金额；
- 人工确认、记录实际支付和生成冲销。

## 6. Excel 定位

现有 `待补SKU成本-shopee.xlsx` 保留，不推倒重做。用户继续填写黄色
“单件成本（人民币）”列，成本口径为每个销售 SKU 的人民币综合单位
成本，不包含广告费、平台佣金和销售端物流费。

采购批次、供应商、采购数量和库存流水不加入 SKU 成本表，避免成本
主数据与进销存重复。表格完成后直接导入 SQLite；以后新增或变更成本
通过 Web 维护，Excel 只用于批量导入、备份和导出。

## 7. 自动化与飞书

Mac 使用 `launchd` 定时执行：

1. 检查紫鸟客户端和 Bridge；
2. 采集订单、广告、退款、物流和库存；
3. 清洗、去重并写入 SQLite；
4. 匹配 SKU 成本并生成订单成本快照；
5. 计算利润、ROAS、现金、库存和对账状态；
6. 运行异常检测和策略分析；
7. 生成日报并发送飞书。

飞书只承担通知和审批，不作为数据维护或事实存储。卡片应提供异常摘要
和回到本地 Web 页面的处理入口。真实广告动作继续受审批、熔断器、
现场激活和精确白名单约束。

## 8. 对账与控制

系统至少执行以下检查：

- 订单号、订单行和平台导出重复检查；
- 所有有效订单 SKU 是否匹配成本；
- 订单数量、退款数量和库存移动是否一致；
- 采购入库、销售出库和期末库存是否满足库存恒等式；
- 平台结算、现金流水和银行余额差额；
- 两位合伙人的 50% 出资目标与实际差额；
- 分润草稿是否与已确认利润期间一致；
- 广告花费是否同时被平台数据和人工费用重复计入；
- 所有计算所需汇率是否存在；
- SQLite 备份和完整性检查是否通过。

对账失败时不生成“已结算”状态，不执行真实广告写操作，并发送飞书
异常提醒。

## 10. 验收标准

- 所有有效订单行均有成本快照或进入明确的待补清单；
- 订单、库存、现金和利润可以从汇总穿透到原始流水；
- 出资按 50%/50% 对账，利润按 60%/40% 分配；
- 所有人工写入具备校验、审计和冲销路径；
- Excel 成本表可无损导入，长订单号和 SKU 不丢失精度；
- 日常任务可由 `launchd` 自动运行并在失败时通知；
- 连续三天真实对账准确率达到 99%；
- `ADWATCH_LIVE_WRITES=false` 保持不变，直至全部现场门禁通过。
