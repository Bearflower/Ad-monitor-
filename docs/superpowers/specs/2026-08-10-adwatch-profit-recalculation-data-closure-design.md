# AdWatch 利润重算数据闭环设计

日期：2026-08-10

## 背景与目标

生产环境的利润重算覆盖了 13 个指标日期，但没有生成利润结果。根因不是 SQLite 损坏，而是三条数据链路的完成口径不一致：退款金额没有可追溯的日期事实、订单成本快照覆盖受订单状态和履约策略阻断、库存页把手工台账数量当成平台 SKU 数量。

本设计的目标是：

1. 对无退款/退货事实的日期，在 T+3 且同步覆盖完整后记录有来源的退款 0。
2. 对存在退货/退款但缺真实金额的日期继续保持待补，禁止用订单实付额猜算。
3. 支持“店铺默认货盘代发、SKU 级自有备货覆盖”的混合履约模型，并按订单日期冻结履约与成本。
4. 把订单成本覆盖、商品单价、退款金额三个缺口分开统计。
5. 让库存页 KPI 使用平台事实并明确标注手工台账口径。

## 已确认业务规则

### 退款 T+3

- 关账日期使用应用配置的业务自然日；经营日 `D` 在 `D + 3` 之后才具备关账资格。
- 关账必须有成功的订单同步运行覆盖该经营日及 T+3 回看范围；没有成功覆盖时保持待补。
- 在完整覆盖范围内没有任何退款/退货观测时，写入每日退款事实：金额为 0、状态为 `t3_closed_zero`、来源为 `t3_no_refund_observed`。
- 只要存在退款/退货状态但观测金额为空，写入 `pending_data`，不生成利润。
- 真实金额来源未来接入时可写入 `observed`，并保留来源、币种和观测时间。
- T+3 关账事实不可修改原始订单或平台退款观测；重新同步必须幂等。

### 混合履约

- 店铺默认履约模式为 `supplier_fulfilled`，按有效日期保存。
- SKU 级履约历史可以覆盖店铺默认，当前模式包括 `supplier_fulfilled` 和 `stocked`。
- 订单履约解析顺序为：已有订单快照、SKU 生效策略、店铺默认策略；解析结果写入订单快照并记录来源。
- 货盘代发订单只要有订单日期有效的 SKU 成本，即可在未发货时冻结订单成本。
- 自有备货订单必须有发货/出库事实且库存足够，才冻结订单成本和出库流水。
- 退货保留原始订单成本快照与退货事实；退货行不计入“仍需扣除的销售商品成本”覆盖缺口，但退款金额仍需满足真实观测或 T+3 规则。

## 数据模型与迁移

新增迁移 29，包含：

### 店铺默认履约历史

`store_fulfillment_history` 以 `platform, store, effective_date` 为主键，保存 `mode, supply_status, note, created_at`。默认值通过有效日期解析，不覆盖已有 SKU 级策略。订单快照的 `resolution_source` 扩展为 `store_default`。

### 每日退款输入

`daily_refund_inputs` 以 `platform, store, data_date` 为主键，保存：

- `refund_amount_original`、`currency`；
- `status`：`observed`、`t3_closed_zero`、`pending_data`；
- `source_type`、`source_ref`、`observed_on`、`closed_at`、`updated_at`。

金额允许为 0，但必须同时有 `observed` 或 `t3_closed_zero` 状态。所有金额使用非负约束，来源引用只保存安全文件名或短标识。

迁移必须对旧库原位执行、单事务失败回滚，并保留现有 `product_costs` 历史数据。旧的无来源退款 0 不自动迁移成已观测或 T+3 关账。

## 服务与数据流

### 退款关账服务

新增 `RefundClosureService`：

1. 读取指标日期、店铺和订单同步运行记录。
2. 计算 T+3 资格，并要求成功同步覆盖回看范围。
3. 汇总 `platform_refund_observations`；有退款状态且金额缺失则写 `pending_data`。
4. 没有任何退款/退货状态且覆盖完整则幂等写 `t3_closed_zero`。
5. 返回每个日期的状态、来源和阻塞原因，供 CLI、重算和页面使用。

`AnalysisRecalculationService` 在每个日期分析前调用该服务。分析读取每日退款事实优先；只有明确的人工/导入输入才允许回退到兼容的 `product_costs` 字段。退款 lineage 使用 `daily_refund_inputs` 作为来源，并写入 `t3_no_refund_observed`、`refund_source_missing` 等细节码。

### 订单成本同步

调整 `OperationsSyncService` 的分支顺序：先解析履约和成本；对 `supplier_fulfilled` 直接冻结成本；仅对 `stocked` 进入订单状态、出库和库存校验。分析 SQL 的预期订单集合排除已确认退货行，实际快照只比较应计销售行，避免退货状态造成假缺口。

### 库存查询与页面

`InventoryService` 提供以下独立查询：

- 平台当前 SKU 数：按最新平台 SKU 映射去重；
- 平台最新库存快照数/总量；
- 手工库存台账 SKU 数；
- 订单成本覆盖缺口：按日期、订单、SKU 和件数统计；
- 商品单价缺口：只统计订单日期没有有效 SKU 成本版本的 SKU。

库存页将“SKU 总数”改为平台 SKU 数，手工台账单独标注；“待补成本”改为订单成本覆盖缺口，并显示具体缺口类型。重算提示统一使用“订单成本覆盖”“商品单价”“退款金额”“T+3 已关账”等标签。

## 错误处理与安全边界

- 部分或失败的订单同步不能触发 T+3 关账。
- 退款状态存在但金额为空时绝不猜算；页面和报表显示待补原因。
- 单个订单成本或履约失败只影响对应日期覆盖，不删除历史事实。
- 迁移、每日退款写入、范围重算均使用事务；报告采用临时文件替换。
- 不记录 Cookie、会话参数、订单买家信息或完整本地路径。

## 测试策略

先写失败测试，再实现最小行为：

1. 迁移和旧库升级、唯一键、金额约束与原子回滚。
2. T+3 未到期、同步部分/失败、无退款关账、存在退款状态缺金额、真实金额和幂等重跑。
3. 店铺默认履约、SKU 备货覆盖、订单快照来源和历史有效日期。
4. 货盘代发未发货冻结成本、自有备货库存校验、退货不制造成本覆盖假缺口。
5. 三类成本/退款缺口分离，lineage 来源和细节码正确。
6. 库存页平台 SKU、平台库存、手工台账和订单成本 KPI 的展示与安全转义。
7. 全量 pytest、作用域 Ruff、compileall、`git diff --check`、SQLite integrity check，以及生产重算接口和页面回归。
