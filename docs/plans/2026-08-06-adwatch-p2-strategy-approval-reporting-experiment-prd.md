## 1. 产品概述

### 1.1 背景

AdWatch 是一个面向 TikTok Shop 与 Shopee 跨境电商团队的本地经营与广告决策系统。P1 阶段已完成数据底座搭建、利润分析、经营账闭环、财务库存和分润等核心能力，全量测试 430 项通过。

P2 阶段在 P1 的基础上，聚焦四个方向：
- **P2-A（已完成）**：Shopee 广告采集从概览级别下钻到 Campaign/SKU 明细级别，引入翻页采集和对账隔离机制
- **P2-B**：将策略规则从"只读查看"升级为"Web 维护"，同时补齐审批执行页面和审计时间线
- **P2-C**：将周报月报从"日报拼接"升级为"独立聚合分析"，并建立每周调度机制
- **P2-D**：引入实验体系框架和备用采集能力，提升数据采集可靠性

### 1.2 业务目标

| 目标 | 说明 | 衡量指标 |
|------|------|---------|
| 下钻分析能力 | 广告分析从平台汇总级下钻到 Campaign/SKU 级别 | 明细覆盖 100% 活跃 Campaign，对账差异不超过 5% |
| 策略自主管理 | 运营人员可直接在 Web 看板创建和管理策略规则版本 | 完成策略规则 Web 表单，替代手动修改数据库 |
| 审批审计闭环 | 审批流全链路可视，审计时间线可追溯 | 审批页面展示所有状态的审批记录，审计时间线按对象分组 |
| 周期性报告 | 周报有聚合和环比，月报有经营利润分析 | 周报含 7 日聚合、环比、TOP/BOTTOM；月报含收入、成本、费用、净利润 |
| 采集可靠性 | 主采集失败后有备用方案，异常可切换 | 主采集连续失败 3 次后自动切换备用采集器 |

### 1.3 用户人群

| 角色 | 描述 | 使用场景 |
|------|------|---------|
| 运营人员 | 日常管理广告投放策略 | 查看策略规则、创建新版本、审批执行、查看周报月报 |
| 合伙人/管理者 | 关注经营利润和趋势 | 查看月报经营利润分析、审批决策 |
| 数据分析师 | 深入分析广告效果 | 对比不同版本策略参数、查看实验分组结果 |
| 系统管理员 | 维护系统稳定运行 | 监控采集器状态、检查备用采集切换 |

## 2. P2-A：Shopee Campaign/SKU 广告明细与分页（已完成）

### 2.1 需求目标

将 Shopee 广告采集从"概览级别"升级到"明细级别"，采集每个 Campaign 下每个 SKU 的独立广告指标，并建立汇总对账机制确保数据一致性。

### 2.2 当前状态（已完成）

- 新增 `SHOPEE_DETAIL_PAGE_SCRIPT` 提取概览 + 明细行 + 分页状态
- 翻页循环（最大 20 页，重试 3 次）
- 明细存储（概览存 `__ALL__`，明细行存真实 campaign_id/sku_id）
- 对账机制：明细合计 vs 概览，超 5% 阈值进隔离
- 新增 `ad_reconciliation_log` 表记录对账日志
- 已在 `PipelineRunner.run()` 中集成对账

### 2.3 关键用户故事

> **US-P2A-01**：作为运营人员，我希望看到每个 Campaign 下每个 SKU 的独立广告指标（花费、销售额、订单数、ROAS），以便定位具体哪个 SKU 的广告效果不佳。

> **US-P2A-02**：作为数据分析师，我希望系统在采集明细后自动对比明细合计与页面概览，如果差异超过 5% 则进入隔离区，避免基于不一致的数据做决策。

### 2.4 验收标准

| 编号 | 验收条件 | 验证方式 |
|------|---------|---------|
| AC-P2A-01 | 采集结果包含每个 Campaign 下每个 SKU 的独立指标行 | 检查 `daily_ad_metrics` 表，sku_id 字段包含真实 SKU ID 而非 `__ALL__` |
| AC-P2A-02 | 翻页循环最多采集 20 页，超出后不再翻页 | 测试夹具模拟 25 页数据，采集结果限制在 20 页 |
| AC-P2A-03 | 翻页失败时最多重试 3 次 | 测试模拟翻页失败，确认重试机制 |
| AC-P2A-04 | 明细合计与概览 KPI 差异在 5% 以内时正常写入 | 对比 `daily_ad_metrics` 中的汇总行与明细行合计 |
| AC-P2A-05 | 明细合计与概览差异超过 5% 时进入隔离表 | 检查 `ad_reconciliation_log` 表，status 为 "quarantined" |
| AC-P2A-06 | 对账日志记录完整，包含概览值、明细合计、差异和阈值 | 检查 `ad_reconciliation_log` 表结构 |

### 2.5 集成点

| 集成对象 | 集成方式 | 说明 |
|---------|---------|------|
| `PipelineRunner.run()` | 方法调用 | 采集完成后自动调用对账方法 |
| `MetricRepository` | 批量 upsert | 明细行批量写入，概览行作为汇总标识 |
| `ad_reconciliation_log` 表 | 写入 | 新增表，记录每次对账结果 |

### 2.6 风险点

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| Shopee 页面 DOM 结构变化 | 明细采集脚本失效 | 使用 `browser_snapshot` 验证，保留 selector 证据截图 |
| 翻页过多导致采集超时 | 采集耗时过长 | 设置最大翻页数 20 页，超时回退到仅概览 |
| 明细与概览持续差异大 | 数据持续进入隔离 | 通过飞书告警通知运营人员，手工确认后调整阈值 |

### 3.4 功能规格

#### F-P2B-01：策略规则 Web 维护表单

**MoSCoW 优先级**: Must

**功能描述**：在 `/strategy-rules` 页面新增"新增版本"表单，支持填写规则参数（JSON 格式）和生效日期，提交后调用 `StrategyRuleService.create_version()` 创建新版本。

**业务规则**：
1. 参数必须为非空 JSON 对象，至少包含 `max_refund_rate` 和 `min_inventory_days` 两个核心参数
2. 生效日期不能与已有版本冲突（同一日期只能有一个生效版本）
3. 新版本自动获取递增版本号，关闭上一版本的生效期
4. 创建成功后跳转到 `/strategy-rules` 页面并显示最新版本信息

**交互说明**：
- 表单包含：`parameters` (textarea, JSON 输入)、`effective_from` (date input)、`created_by` (text input)
- 参数输入框提供 JSON 格式校验，格式错误时显示红色提示
- 提交按钮带防重复提交保护（提交后禁用直至响应返回）

**验收标准**：

| 编号 | 验收条件 | 验证方式 |
|------|---------|---------|
| AC-P2B-01 | 提交有效参数和生效日期后，新版本成功创建 | 验证 `strategy_rule_versions` 表新增记录，版本号递增 |
| AC-P2B-02 | 提交空参数时显示错误提示，不创建版本 | 验证版本表无变化，页面显示错误信息 |
| AC-P2B-03 | 提交与已有版本冲突的生效日期时显示错误提示 | 验证 `StrategyRuleError` 异常被捕获，页面显示冲突提示 |
| AC-P2B-04 | 创建成功后页面自动跳转到 `/strategy-rules` | 验证 HTTP 303 响应 |
| AC-P2B-05 | 提交不合法 JSON 时显示格式错误提示 | 验证前端 JSON 校验拦截 |

#### F-P2B-02：审批执行页面

**MoSCoW 优先级**: Must

**功能描述**：重构 `/approvals` 页面，从占位页面升级为完整的审批列表页，展示所有审批请求及其状态，支持按状态筛选和详情展开。

**页面结构**：
1. 审批总览 KPI：待审批数、已批准数、已拒绝数、已过期数
2. 审批列表表格：创建时间、建议内容、状态、决策时间、决策人
3. 状态筛选器：全部 / 待审批 / 已批准 / 已拒绝 / 已过期
4. 详情展开：点击行展开显示完整建议内容、决策证据、执行结果

**业务规则**：
1. 审批状态机：`pending` -> `approved` / `rejected` / `expired`
2. 超过 24 小时未决策的审批自动标记为 `expired`
3. 已过期的审批不可再决策

**验收标准**：

| 编号 | 验收条件 | 验证方式 |
|------|---------|---------|
| AC-P2B-06 | 页面展示所有审批记录，按创建时间降序 | 检查审批列表渲染结果 |
| AC-P2B-07 | 按状态筛选后只显示对应状态的审批 | 测试筛选参数 |
| AC-P2B-08 | 过期审批自动标记 `expired` 状态 | 测试过期检测逻辑 |
| AC-P2B-09 | 点击行展开显示完整详情 | 检查展开后的 HTML 内容 |

#### F-P2B-03：审计时间线

**MoSCoW 优先级**: Should

**功能描述**：新建 `src/adwatch/audit/service.py` 模块，提供审计事件查询和时间线生成功能，在 `/approvals` 页面集成审计时间线可视化。

**功能点**：
1. `AuditService.list_events(object_id, object_type)`：按对象 ID 和类型查询审计事件
2. `AuditService.get_timeline(object_id)`：生成时间线数据（按时间排序的事件序列）
3. 时间线渲染：在审批详情中以时间线卡片形式展示

**审计事件类型**：
- `strategy.version.created`：策略版本创建
- `strategy.version.activated`：策略版本生效
- `strategy.version.deactivated`：策略版本关闭
- `approval.created`：审批创建
- `approval.decided`：审批决策
- `approval.expired`：审批过期

**验收标准**：

| 编号 | 验收条件 | 验证方式 |
|------|---------|---------|
| AC-P2B-10 | 审计事件按对象 ID 查询返回正确结果 | 测试 `list_events()` 方法 |
| AC-P2B-11 | 时间线按时间顺序排列，包含事件类型、时间、操作人 | 测试 `get_timeline()` 方法 |
| AC-P2B-12 | 时间线在审批详情页中正确渲染为卡片 | 检查页面 HTML 结构 |

#### F-P2B-04：Shadow 模式 UI

**MoSCoW 优先级**: Could

**功能描述**：在 `/strategy-rules` 页面新增"Shadow 评估"按钮，点击后执行策略规则评估但不写入 `recommendations` 表，结果展示在页面上供运营人员预览。

**交互说明**：
- 点击"Shadow 评估"按钮后，页面发起 POST 请求到 `/strategy-rules/shadow`
- 后端执行 `recommend()` 方法，结果暂存到 `shadow_results` 临时表或日志
- 前端展示评估结果（建议动作、证据列表、预期效果）
- 评估结果不持久化到 `recommendations` 表

**验收标准**：

| 编号 | 验收条件 | 验证方式 |
|------|---------|---------|
| AC-P2B-13 | Shadow 评估执行后 `recommendations` 表无新增记录 | 对比评估前后的 `recommendations` 表记录数 |
| AC-P2B-14 | 评估结果正确展示在页面上 | 检查页面渲染结果 |
| AC-P2B-15 | 多次 Shadow 评估互不影响 | 连续执行 2 次评估，检查结果正确性 |

### 4.3 关键用户故事

> **US-P2C-01**：作为运营人员，我希望每周一早上收到上周的广告周报，包含 7 日聚合数据、环比变化、TOP/BOTTOM SKU 和风险摘要，以便快速掌握上周整体表现。

> **US-P2C-03**：作为运营人员，我希望周报月报有缺日提示，如果某天数据缺失，报告中明确标注"缺日"，避免基于不完整数据做决策。

### 4.4 功能规格

#### F-P2C-01：周报聚合与环比

#### F-P2C-03：独立报告调度

**功能描述**：建立独立的周报/月报调度机制，支持每周一自动生成周报、每月初自动生成月报，通过飞书 webhook 推送。

**调度规则**：
1. **周报**：每周一 09:30 自动生成上周（周一~周日）周报，发送到飞书
2. **月报**：每月 1 日 09:30 自动生成上月月报，发送到飞书
3. **锁机制**：使用 `scheduler_locks` 表防止重复触发（同一报告类型 + 同一周期只能执行一次）
4. **故障通知**：周报/月报生成失败时，通过飞书发送故障通知

**实现方式**：
- 新增 `scheduler_locks` 表，记录各报告类型的锁状态
- 修改 `scheduled_daily.py`，新增 `run_weekly_report()` 和 `run_monthly_report()` 方法
- 通过 macOS LaunchAgent 的 `StartCalendarInterval` 配置每周一和每月 1 日的调度

**验收标准**：

| 编号 | 验收条件 | 验证方式 |
|------|---------|---------|
| AC-P2C-10 | 每周一自动触发周报生成，锁机制防止重复 | 测试调度器触发逻辑 |

| AC-P2C-13 | 生成失败时发送飞书故障通知 | 测试故障通知逻辑 |

### 5.3 关键用户故事

> **US-P2D-01**：作为运营人员，我希望创建 A/B 实验来测试不同的广告策略，系统自动将 Campaign 分配到实验组或对照组，并记录实验期间的关键指标。

### 5.4 功能规格

#### F-P2D-01：实验分组与状态机

**MoSCoW 优先级**: Must

**功能描述**：新建 `src/adwatch/experiments/` 模块，包含实验分组、状态机和护栏条件管理。

**核心模型**：
1. **ExperimentGroup**：实验分组，按 `store_id` 或 `campaign_id` 哈希分桶
   - 支持 50/50、80/20、70/30 等比例
   - 同一对象始终分配到同一组（确定性哈希）
2. **ExperimentWindow**：实验窗口，定义实验的开始和结束时间
3. **ExperimentGuardrail**：护栏条件
   - 最小样本量（如每个变体至少 100 单）
   - 最小运行天数（如至少运行 3 天）
   - 其他条件（如熔断器状态、数据质量）
4. **ExperimentStatus**：状态机
   - `draft` -> `running` -> `completed` / `stopped` / `failed`

**业务规则**：
1. 实验创建后进入 `draft` 状态，可编辑参数
2. 启动实验时检查所有护栏条件，通过后进入 `running` 状态
3. 运行中的实验可手动停止（`stopped`）或自动完成（`completed`）
4. 护栏条件不满足时，实验启动失败并记录原因

**验收标准**：

| 编号 | 验收条件 | 验证方式 |
|------|---------|---------|
| AC-P2D-01 | 同一 `store_id` 始终分配到同一实验分组 | 多次哈希验证一致性 |
| AC-P2D-02 | 实验启动时检查护栏条件，不满足时阻止启动 | 测试护栏条件检查逻辑 |
| AC-P2D-03 | 实验状态机状态转换正确 | 测试所有状态转换路径 |
| AC-P2D-04 | 支持 50/50、80/20、70/30 分组比例 | 测试不同比例的分组结果 |

#### F-P2D-02：商品测试与 A/B 实验服务

**MoSCoW 优先级**: Should

**功能描述**：实现实验管理服务，支持创建实验、分配变体、记录操作时间线。

**功能点**：

2. `ExperimentService.assign_variant()`：为指定对象分配变体

- `experiment.started`：实验启动
- `experiment.completed`：实验完成

#### F-P2D-03：备用采集与自动切换

**MoSCoW 优先级**: Must

**功能描述**：新建备用采集器，在主采集器连续失败时自动切换，确保数据采集不中断。

**备用采集器**：
1. `collectors/fallback.py`：备用采集器抽象和切换逻辑
2. `collectors/browser_use.py`：基于 browser-use（通过 Ziniao CLI 通用浏览器能力）的备用采集实现

**切换逻辑**：
1. 主采集器连续失败 3 次后，自动切换到备用采集器
2. 备用采集结果标记 `source="fallback"` 或 `source="browser-use"`
3. 切换事件记录到审计日志
4. 备用采集器也失败时，记录故障并继续尝试主采集器
5. 备用采集成功恢复后，维持备用模式直至手动切回或主采集器连续成功 3 次

**集成方式**：
- 修改 `daily_run.py` 中的 `ProductionDailyRunDependencies.collect()` 方法
- 在采集循环中检测失败次数，超过阈值时切换采集器
- 复用 `CircuitInputs` 和 `evaluate_circuit()` 的熔断判断（可选）

**验收标准**：

| 编号 | 验收条件 | 验证方式 |
|------|---------|---------|
| AC-P2D-09 | 主采集器连续失败 3 次后自动切换到备用采集器 | 测试模拟连续失败场景 |
| AC-P2D-10 | 备用采集结果标记为 `source="fallback"` | 验证采集结果 source 字段 |
| AC-P2D-11 | 切换事件记录到审计日志 | 验证 `audit_events` 表记录 |
| AC-P2D-12 | 备用采集器也失败时记录故障，不阻塞整体流程 | 测试双失败场景 |
| AC-P2D-13 | 主采集器连续成功 3 次后自动切回主采集器 | 测试恢复逻辑 |
