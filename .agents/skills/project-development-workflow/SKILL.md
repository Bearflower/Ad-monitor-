# 项目开发工作流

## 规则来源

开始实现前，从仓库根目录完整读取：

- `.trae/rules/coding-standards.md`
- `.trae/rules/development-workflow.md`

同时读取 `README.md`、`docs/README.md`，以及与当前任务直接相关的需求、设计、计划、配置和实现。`.trae` 文件是详细历史规则来源；本技能负责把它们适配为当前 Codex 工作流。

## 适配原则

- 用户已经明确要求修改时，不要仅因旧规则中的固定确认模板重复索要确认；存在会实质改变结果的选择或需要扩大权限时才暂停。
- 将 Trae 的智能体名称理解为职责，例如需求分析、架构、实现、检查、测试和文档维护。使用当前可用工具或技能承担这些职责；不存在同名能力时不得声称已调用。
- 计划和协作深度应与风险和改动规模匹配。小改动仍需验证，但无需伪造完整多智能体流水线。
- 当前仓库事实、用户指令和平台安全边界优先。旧规则中的其他项目路径、命令、服务或示例不得直接套用。

## 执行要求

1. 明确预期行为、验收条件和不在范围内的内容；先检查工作区，保留用户已有改动。
2. 查找现有模块、配置键、API 签名和测试模式。优先复用现有依赖和公共模块。
3. 新增或改变行为时先建立能失败的验证；修复缺陷时先复现问题。配置或纯文档变更使用等价的结构、引用和场景检查。
4. 实现最小必要改动。业务阈值、评分、延迟和策略参数必须可追溯到配置或算法；禁止无依据硬编码。
5. 禁止在生产服务器运行回测。需要远程数据时，只在远程筛选或导出，然后在本地回测。
6. 逐项验证 import、方法与参数、配置键、路径、变量、分支方向、异常路径、同步/异步边界、硬编码来源和文件完整性。
7. 运行相关测试和静态检查；高风险或跨模块改动再运行完整测试。检查行为、API、配置和操作方式变化是否需要更新 `docs/`。
8. 汇报修改文件、验证命令及结果、未验证部分和遗留风险。不要自动提交、推送或部署。

## 完成检查

- 引用的模块、API、配置键和文件真实存在。
- 测试覆盖新增或修复的行为，并已观察到有意义的失败与通过。
- 代码与相关文档一致，没有把敏感信息写入代码、日志或文档。
- 只有用户明确要求时，才转入 `$project-git-workflow` 或 `$project-deployment-workflow`。
