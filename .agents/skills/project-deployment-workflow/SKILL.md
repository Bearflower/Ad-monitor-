# 项目部署工作流

## 规则来源与停止条件

完整读取 `.trae/rules/deployment.md`，再读取当前仓库的 `README.md`、相关 `docs/` 部署文档、Docker/服务配置和现有部署脚本。需要远程部署时，使用当前可用的服务器部署技能或工具，但必须服从本技能的项目边界。

旧规则包含 Binance 项目的示例路径、策略文件、容器名、服务器占位符和 Docker 命令。它们只说明验证思想，绝不是本仓库的部署参数。无法从当前配置或用户信息解析真实目标、认证方式、目录、服务名、容器名、健康检查或回滚方法时，停止并请求必要信息。

部署属于外部写操作。用户必须明确授权目标环境；生产环境、删除旧镜像、清理全部构建缓存、覆盖远端目录或其他难恢复动作需要单独核实具体目标与恢复路径。任何关键阶段失败都必须停止，不得继续启动旧产物并宣称成功。

## 部署流程

1. **解析目标：** 确认仓库、分支或提交、环境、主机、远端目录、服务/容器、部署方式、健康检查和回滚方案。记录部署前状态。
2. **本地关卡：** 检查工作区、版本和相关测试。禁止在生产服务器运行回测；需要的数据先导出到本地。
3. **打包关卡：** 优先使用仓库已有脚本或可审计的 Git 文件清单。排除 `.env`、密钥、SQLite、日志、缓存、临时文件和本地产物；生成唯一版本标记和关键文件摘要。
4. **上传关卡：** 上传后比较本地与远端包的 SHA-256 或平台等价摘要。摘要不一致立即停止。
5. **构建关卡：** 使用仓库真实构建方式并保留完整退出码和日志。构建失败不得继续使用旧镜像或旧服务冒充成功。
6. **启动与版本关卡：** 验证目标服务实际运行、容器使用预期镜像、版本标记一致、关键运行文件摘要一致。卷挂载存在时同时核对宿主机来源。
7. **功能关卡：** 执行仓库定义的健康检查或最小烟雾测试，检查新启动后的错误日志和关键业务开关。
8. **确认报告：** 记录时间、环境、提交/版本、产物摘要、服务状态、代码一致性、健康检查、未解决警告和回滚点。

## 禁止虚假成功

- 容器处于 running 状态不等于新代码已部署。
- 镜像创建时间新不等于容器使用了该镜像。
- 上传命令退出成功不等于文件完整。
- 日志中存在错误、版本或关键文件不匹配时，不得报告部署成功。
- 无法完成某层验证时，明确标记“未验证”，说明原因和风险，不得用推测替代证据。
